## 2026-08-28 — 跨仓 token 守卫挂在云端 CI，脚本不再有默认路径

### 决定

设计 token 的跨仓比较（`scripts/check-token-parity.cjs`）由
**`.github/workflows/ci.yml` 的 `tokens` job** 运行：它把边缘仓克隆到 checkout
的兄弟目录，然后显式传入两个根。同时**删掉脚本里的默认路径** ——
不带参数现在明确 exit 2，且每次运行都先打印它真正读到的两个绝对路径与两个 HEAD。

### 为什么是云端 CI，不是边缘 CI

`scripts/sync-contract.sh` 的文件头写着：**边缘仓库得能独立构建和跑 CI，
不能依赖旁边有没有这个仓库。** 让边缘 CI 去克隆云端会直接违反那条已经写下的决定；
云端这边**没有对应的独立性要求**。放云端是在保住那条决策，而不是花掉它。

「云端 CI 检不出边缘仓」这句话此前出现在多处，理由是「每个 CI 只 checkout 一棵树」——
那是**配置，不是能力**。两个仓都是公开的，无凭证 `git ls-remote` 返回的 SHA
与本地逐字符相同（阴性对照：不存在的仓 exit 128）。不需要任何密钥。

可照搬的先例是**边缘 CI 自己**：它已经在生产里把只读的 vowifi-go 镜像克隆到
`$GITHUB_WORKSPACE/..`，再比对两棵树。`sync-contract.sh` **不是**先例 ——
它是写入器不是检查器，而且从来没有任何东西自动运行过它。

### 为什么必须删掉默认值

那两个默认值是一台工作站的硬编码绝对路径，是一个**活的假绿源**：
在任何别的机器上它 exit 2、从未真正运行过；在那台机器上它**从任何目录**跑起来
都静默地去评分两棵主树。实测：一份 `--touch` 真的改坏了的一次性副本，
在副本目录里跑无参数形式返回 `PARITY OK` exit 0。这个仓有三十个 worktree。

🔴 更值得记的是它对**证据**做了什么：有人跑无参数形式并得到了正确答案，
只是因为他当时改的恰好就是那两棵主树 —— **那是运气不是设计，而输出里没有任何
东西能把这两种情况区分开。** 所以「我亲手验过」在站在默认值上时，
并不比一次转述更可靠。修法与这个板子反复得到的结论一致：
**让工具自己说出它读了什么，并拒绝猜。**

### 约束了什么

- **两端都要动的 token 改动，必须先合边缘再合云端。** job 读的是边缘 `main`，
  反过来做云端 PR 会一直红到边缘合并为止。**那是守卫在起作用**，不是坏了。
  只有一个方向要排队，因为只有一侧在检查。详见 `deploy/RUNBOOK.md`。
- **不许为了「让历史 commit 可复现」去 pin 边缘 ref。** pin 等于退回被否决过的
  两份快照方案：每个仓的作者都能改自己那份，于是两边 CI 全绿而仓库真的漂了。
- **调用它必须显式传两个根。** 无参数、单参数、以及 `--edge <path>` 全部 exit 2。
- 边缘单边漂移在云端没有 push 时不会被发现。`schedule:` 能缩短这个窗口，
  但 `on:` 是本文件所有 job 共用的，加它等于把 postgres `migrations` job
  也放上定时器 —— 那是改动其它四个 job，不是新增。

## 2026-08-22 — VoWiFi、语音通话、SM-DP+ 全部要做

### 决定

三项此前悬而未决的能力全部纳入路线图：

| 能力 | 决定 | 范围 |
| --- | --- | --- |
| VoWiFi / IMS | 做 | **仅针对美国卡** |
| E911 地址登记 | 做 | 跟随 VoWiFi，仅美国 |
| 语音通话 | 做 | 拨号、接听、挂断、媒体流；**重点发展方向** |
| SM-DP+ Profile 下载 | 做 | 完整 ES9+ 链路 |

### 为什么

VoWiFi 限定美国不是技术取舍而是监管现实：E911 是美国的法定要求，
其它市场没有对应义务，为它们实现一套用不上的地址登记只会增加攻击面。
VoWiFi 本身在漫游省费上对任何市场都有价值，但先做美国这一条完整链路，
比同时铺开半条要有用。

语音通话被明确为要大力发展的能力。这把它从"可选功能"变成了会影响架构的
约束：媒体面（RTP）与信令面（SIP/IMS）的时延要求和短信完全不同，
命令中继那种"下发—执行—回执"的异步模型承载不了通话。

### 这个决定暴露的前置条件

做完决定后清点了台上硬件，发现一件改变排期的事：

```
862547055142811  eUICC 一个 profile：Club     8985…9571  香港 CSL
867018069514820  eUICC 一个 profile：WEBBING  8985…4201  香港 CSL
867018069509705  开 ISD-R 通道失败，很可能无 eUICC       中国移动实体卡
```

**台上没有任何美国卡。** Saily 是 eSIM 供应商，它的美国 profile 需要
通过 SM-DP+ 下载到 eUICC 上才会存在。

因此 **SM-DP+ 下载是 VoWiFi 与 E911 能够被验证的前置条件**，
而不是可以排在它们之后的独立项目。原计划把 SM-DP+ 放在阶段 3、
VoWiFi 放在阶段 4，顺序是对的但理由错了 —— 真正的理由不是
"eSIM 功能应该先补齐"，而是"没有它就没有美国卡可测"。

同一份清点也再次确认了 X-06 演练为什么一直做不了：每个 eUICC 只有
一个 profile，禁用它就等于让卡脱网且没有回滚路径。
下载能力同时解开了这个死结 —— 有了第二个 profile 才敢切换。

### 约束了什么

- 阶段 3（eSIM）必须在阶段 4（VoWiFi/语音）之前完成，且不能只做一半：
  ES10b 的通知处理是下载流程的一部分，不是可选装饰。
- 语音通话不能沿用命令中继。需要为实时媒体设计单独的通道，
  这是阶段 4 的第一个技术问题，不是最后一个。
- E911 的 websheet 代理在多租户云上与单机上的 SSRF 爆炸半径不同，
  必须真正沙箱化，不能照搬旧版实现。

## 2026-08-22 — 插件系统不移植

见 [plugins-not-ported.md](plugins-not-ported.md)。

简述：旧版的插件是在运行控制台的机器上 `exec` 一个上传来的二进制。
这在机器属于安装者本人时是合理的，在多租户云上则完全移除了租户隔离 ——
RLS 由 PostgreSQL 针对会话变量强制执行，而插件后端根本不走 PostgreSQL 会话。
