# 路线图

目标与分阶段计划。决策依据见 [decisions.md](decisions.md)，
与旧版 VoDoge、开源项目 VoCat 的逐条功能对照见同名 artifact。

---

## 目标

**让一张美国 eSIM 在我们的硬件上完成一次 VoWiFi 语音通话，全程从云端控制台操作。**

选这个作为北极星，是因为它恰好串起了整条链路上每一个还缺的环节：

1. 要有美国卡 → 需要 SM-DP+ 下载
2. 下载要安全 → 需要 ES10b 的通知处理与第二个 profile 作回滚
3. 通话要能打 → 需要 IMS 栈与实时媒体通道
4. 美国要合规 → 需要 E911 地址登记
5. 全程云端操作 → 需要控制台把这些都暴露出来

任何一环缺失，这句话就说不出口。反过来，这句话成立时，
阶段 1 到 4 的实质内容也就都在了。

### 完成的判据

不是"代码写完"，而是这一串在真机上依次为真：

- 控制台里输入一个 Saily 激活码，profile 下载到台上的 eUICC
- 切换到该 profile，卡注册上美国运营商，控制台显示 MCC 310/311
- 在控制台登记 E911 地址，运营商侧确认
- VoWiFi 隧道建立，IMS 注册成功
- 从控制台发起一次通话并接通

## 当前进度

截至 2026-08-22，逐条核对代码而非凭记忆：

**已完成并已验证**

- 上行链路本身。积压 2370 条已排空到 0，稳态约 0.23 行/秒。
  修掉的是：重复投影触发器、缺少的 `status`、jsonb 存不下的 NUL、
  丢弃记录不消费序号、缺口回退造成的自我洪泛、TCP persist 卡死、
  被顶替会话不关闭、空闲会话不回收。
- 入站短信解码。GSM-7 此前根本没解码过。解码器已从
  `#[cfg(target_os = "linux")]` 里搬进 `edge-core`，可在任何机器上测。
- 通知的三个渠道与两个事件（见阶段 1）。
- 过期命令回收。

**已知但未处理**

- 新短信的端到端验证。解码器有完整单测（3GPP 参考向量等），
  但还没有一条真实新短信走完全链路，库里现存的都是旧二进制入队的存量。
- 一条 `accepted` 命令的 outbox 记录始终未 resolve，是
  `apply_command_receipt` 的账目遗留。不会导致重发。
- 过期回收只在设备 resume 时触发。`app.tenants` 带 FORCE RLS 且按当前租户隔离，
  没有任何东西能枚举租户做全局清扫，所以不回来的设备会一直留着陈旧记录。

## 阶段

| 阶段 | 内容 | 预估 | 依赖 |
| --- | --- | --- | --- |
| 1 | 把已有的东西接通 | 1 周 | 无 |
| 2 | 自动化与远程控制 | 1.5 周 | 阶段 1 的通知投递 |
| 3 | eSIM 完整能力 | 3 周 | 无（可与 1、2 并行） |
| 4 | VoWiFi 与语音 | 4 周 | **阶段 3 必须完成** |
| 5 | 收尾 | 1 周 | 无 |

阶段 3 是关键路径。它不完成，阶段 4 连测试用的卡都没有。

### 阶段 1 — 把已有的东西接通

半条链路已经在的项目，投入产出比最高。

- **通知真的发出去** —— *部分完成*。Webhook / 邮件 / Bark 三个渠道已实现并接线，
  入站短信与命令失败会触发。**仍缺**：设备掉线、契约违规两个事件类型已定义但无人触发；
  备份失败连事件类型都没有；投递是尽力而为，没有重试。
- **短信补齐** —— 解码已修好（GSM-7 / UCS-2 / 8bit、拼接、地址）。**仍缺**：
  联系人列表、未读状态、`+CDS` 网络送达回执、发送限额真正生效
  （`hourly_limit` 目前只在设置里校验和存储，发送路径上没有任何地方读它）。
- **设备操作补齐** —— 重扫描、刷新缓存、数据网络启停、USBNET 模式。
- **发现未纳管硬件** —— 边缘知道插了几根棒子，云端只看得到已注册的。
- **公网 IP 与主机状态** —— 代理场景最常问的数；顺带带上边缘的 CPU / 内存。
- **日志保留** —— `app.ingress` 已三万余行且在长，机器只有 40G。

### 阶段 2 — 自动化与远程控制

- **定时任务** —— 定时发短信 / 拨号 / 查公网 IP。重试语义要照 VoCat 的教训：
  进了模组或 IMS 事务的不重试，只有准备阶段的失败可以安全重试。
- **通知渠道补齐** —— Telegram、飞书、企业微信、Pushplus。
- **Telegram 机器人** —— 查状态、切 profile、发短信；敏感操作二次确认。
  多租户下要按租户绑定 chat，这是我们比 VoCat 复杂的地方。
- **只读账号** —— 现在只有单一操作员角色。

### 阶段 3 — eSIM 完整能力（关键路径）

- **ES10b** —— EID 边缘已能读（ISD-R / GET DATA `5A`），云端没有接。
  **仍缺**：芯片信息、通知列表与重试。下载流程依赖通知处理，它不是可选装饰。
- **禁用 / 重命名 / 删除 profile** —— 边缘 ES10c 有 enable / disable 的 APDU，
  云端已有 `list_esim_profiles` 与 `switch_esim_profile`。**仍缺**：
  禁用与删除的云端命令，以及重命名（边缘也还没有）。
- **SM-DP+ 下载** —— ES9+ 的 HTTPS 栈、与 eUICC 的双向认证、通知回执。
  这是整条路线上最大的单项。

### 阶段 4 — VoWiFi 与语音

- **实时媒体通道** —— 第一个技术问题而非最后一个。命令中继的
  "下发—执行—回执"异步模型承载不了通话。
- **IMS 栈** —— IKEv2 / ePDG 隧道、EAP-AKA 认证、IMS 注册。
- **VoWiFi 启停与重连**、**IMS 短信**。
- **语音通话** —— 拨号、接听、挂断、媒体流。
- **E911 地址登记** —— 仅美国。websheet 代理必须真正沙箱化。

### 阶段 5 — 收尾

- Profile ↔ 代理绑定、UDP Associate 探测、PC/SC 读卡器
- OpenAPI 文档、发布制品与更新检查
